# Code Campus — project notes

## Node version

Use Node **24.20+** (`.nvmrc` is set to this). `jsdom` (used by vitest) requires
it — don't trust the README/SETUP.md's "18+/20+" claim, that's stale.

## Dependency versions are pinned on purpose — don't "helpfully" bump them

Several packages here are pinned *below* their absolute latest because the
latest published version is a breaking preview/rewrite that doesn't work
with the rest of this stack. If `npm outdated` suggests bumping these,
don't, without re-verifying the whole toolchain:

- **`prisma` / `@prisma/client` → `6.19.3`**, not 7.x or 8.x. Prisma 8 is a
  totally different platform CLI (no `generate`/`migrate`/`db push`). Prisma 7
  also drops the classic `datasource { url }` schema syntax this project uses.
- **`typescript` → `6.0.3`**, not 7.x. TS7 is the new native compiler;
  `typescript-eslint` doesn't support it yet.
- **`eslint` → `9.39.5`**, not 10.x. `10.9.1` crashes at runtime against
  `typescript-eslint` (`scopeManager.addGlobals is not a function`).

ESLint config is flat-config (`eslint.config.mjs`) — `next lint` and
`.eslintrc.json` don't exist/work anymore in this Next 16 + ESLint 9 setup.
Run lint via `npm run lint` (→ `eslint .`).

## Pyodide is self-hosted — don't move the worker back into src/workers/

`public/workers/pyodide-worker.js` is a **plain static JS file**, deliberately
*not* compiled through Next's `new Worker(new URL('./file', import.meta.url))`
bundling. That's required, not a style choice: Next/Turbopack's dev-mode
worker bundler always wraps worker chunks in a bootstrap script that uses
`importScripts` to chain-load them, regardless of the `{ type: 'module' }`
option passed to the `Worker` constructor. Pyodide (since ~v300+) refuses to
run at all if `importScripts` exists in the worker's global scope. The only
way to get a genuine module worker (no `importScripts` in scope) is to load
it via a literal string URL pointing at a static file, bypassing Next's
special bundling entirely — hence it lives in `public/`, not `src/`.

`public/pyodide/*` (the actual Pyodide runtime — `.wasm`, stdlib zip, etc.) is
**gitignored** and regenerated by `scripts/copy-pyodide-assets.js`, which runs
automatically via the `postinstall` npm script. It copies whatever version is
installed from `node_modules/pyodide`, so it can't drift from `package.json`.
If Pyodide ever fails to load, first check `public/pyodide/` actually exists
(run `npm install` if not) before assuming it's a code bug.

## Local dev

- Dev server runs on **port 3007** (`npm run dev`), not the Next default 3000.
- `DATABASE_URL` points at a Postgres instance you run yourself — there's no
  `docker-compose`-managed Postgres in this project (removed on purpose; it
  conflicted with an already-running Postgres container).
- Two env files exist: `.env.local` (Next.js reads this) and `.env` (the
  Prisma CLI only reads `.env`, not `.env.local`) — keep both in sync if you
  change `DATABASE_URL` or other values Prisma needs at the CLI.
- `npm run seed` creates three test accounts — `admin@example.com`,
  `instructor@example.com`, `student@example.com` — all with password
  `password`. There's no admin UI for user management yet, so this is
  currently the only way to get non-empty accounts into the database.

## Architecture

- `/server` has zero Next.js imports by design — it's the extraction
  boundary for a future standalone backend service.
- File content is stored in **both** Postgres (`ProjectFile.content`) and the
  local filesystem (`./storage/<uuid>`, via `LocalFilesystemStorage`) on every
  write, but only the Postgres copy is ever read back — the filesystem write
  is currently redundant, kept because `IStorageService` is designed to be
  swapped for S3/MinIO later.
- TanStack Query is wired up (`QueryProvider` in `src/app/layout.tsx`) for all
  server state. Zustand is an installed dependency but intentionally unused —
  no cross-route state currently needs it; don't add a store without a real
  reason.
